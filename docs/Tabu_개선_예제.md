# 개선형 Tabu Search 예제

제출 파일은 [example_tabu_advanced.py](../examples/example_tabu_advanced.py)입니다.
이 파일 하나에 필요한 함수가 모두 들어 있고, `math`와 `pandas`만 import합니다.
엔진 내부 모듈·파일·선수 ID의 고정 목록에 의존하지 않으며, 난수는 전달받은 `rng`만 사용합니다.

## 무엇을 바꿨나요?

| 항목 | 기존 Tabu 예제 | 개선형 |
|---|---|---|
| 공격 선수 | 먼저 고른 9명을 유지 | 타순 교환과 벤치 선수 교체를 함께 탐색 |
| 공격 평가 | OPS·OBP·SLG와 현재 체력 | 사건별 기록의 표본 보정, 상대 투수·맞대결, 예상 체력 반영 |
| 타순 | 고정 타순 가중치와 시작 위치 보정 | 실제 선두부터 평가한 뒤 엔진의 시작 인덱스에 맞춰 반환 |
| 수비 평가 | 수비 명단의 타격 능력에도 가점 | 공격·수비 명단이 독립이므로 실책 비용과 향후 타격 체력 손실을 평가 |
| 투수 | ERA·기초 스태미너·현재 체력 | 누적 투구 수와 목표치로 추가 4·12·22구 시점의 실점 위험을 근사 |
| 타부 | 이동한 배정 일부를 금지 | 빠진 선수가 원래 슬롯으로 복귀하는 역이동을 금지. 교환은 두 슬롯 모두 기록 |

이번 엔진에서는 좋은 타자를 수비에 넣어도 공격에 자동 출전하지 않습니다.
오히려 수비 시작마다 스윙 환산 3~5회의 체력을 소모하므로, 향후 타격 기여가 큰 선수의 체력을
수비에 쓸 때의 비용을 고려하는 것이 개선의 핵심입니다.
그 결과 상대적으로 약하거나 지친 타자가 수비에 나오거나, 포수 자리에 다른 포지션의 타자가 나올 수 있습니다.
현재 엔진의 허용 명단·타구 처리 규칙을 이용한 선택이며, 실제 야구 전체에 적용할 전략은 아닙니다.

## 탐색 구조

해는 타자 9명의 슬롯 배정입니다. 공격과 수비 모두 같은 `_tabu()` 탐색기를 사용합니다.
두 슬롯을 교환하거나 벤치 선수 한 명으로 교체하므로 중복 없는 합법적인 명단을 유지합니다.
투수는 야수 배정과 독립이므로 별도로 모든 후보를 비교합니다.

초기해에서 시작해 현재 해보다 나쁜 이동도 허용하되, 지금까지 가장 좋은 해를 별도로 보존합니다.
최근 이동의 역이동을 금지하고, 전체 최고 점수를 개선할 때는 타부를 해제하는 열망 기준을 적용합니다.
개선이 정체되면 최고해를 섞어 다른 배치에서 다시 탐색합니다.

반복은 80회, 반복당 이웃은 40개입니다. 벽시계 시간에 따라 중단하지 않으므로 같은 입력과 `rng`에서
결과가 재현됩니다. 실제 제한시간에는 프로세스·import 비용도 포함되므로 제출 환경에서 검사하세요.

평가식은 기대 득점의 근사입니다. `PRIOR`, `RUN_WEIGHTS`, 수비 기회비중과 체력 손실 가중치는
예제에서 정한 가정이며 실제 선수의 숨겨진 성향이나 정확한 엔진 확률을 읽어오는 값이 아닙니다.

## 실행과 비교

프로젝트 최상위에서 환경을 활성화한 뒤 실행합니다.

```shell
python -m kbo_sim.server --a-name 개선Tabu --a-team 삼성 --a-algo examples/example_tabu_advanced.py --b-name 기존Tabu --b-team KT --b-algo examples/example_tabu_lineup.py --seed 42
```

아래 도구는 삼성/KT, LG/KIA, 두산/NC, 롯데/SSG, 한화/키움의 다섯 조합에서
같은 시드마다 알고리즘의 팀·홈/원정 배정을 뒤바꿔 두 경기를 실행합니다.

```shell
python tools/compare_tabu.py --check --seeds 4 --seed-start 710000 --out output/tabu_comparison.json
```

`--check`는 10개 구단의 실제 업로드 검사(공격·수비 각각 1회)와 지친 상태·빈 맞대결 표·재현성을 확인합니다.
기본 비교 모드는 **이 저장소의 두 예제만 같은 프로세스에서 실행**해 반복 실험 시간을 줄입니다.
매 호출 새 모듈을 불러오고 실제 경기 엔진과 명단 검증을 사용하지만, 하드 타임아웃과 프로세스 격리는 적용하지 않습니다.
따라서 빠른 모드의 호출시간을 실제 채점 시간으로 해석하지 마세요.

일반 서버와 같은 격리 실행 방식으로 비교하려면:

```shell
python tools/compare_tabu.py --isolated --seeds 1 --pairs 1 --seed-start 310000 --out output/tabu_isolated.json
```

`--seeds`는 구단 조합별 시드 수이고 `--pairs`는 앞에서부터 사용할 구단 조합 수입니다.
총 경기 수는 `seeds × pairs × 2`입니다. JSON에는 경기별 시드·배정·점수·승자, 호출시간과 폴백 횟수를 저장합니다.

## 측정 결과

현재 동봉된 10개 구단 데이터와 같은 버전의 두 알고리즘을 사용했습니다.
첫 20경기 결과를 본 뒤 알고리즘을 변경하지 않고, 겹치지 않는 시드 40경기로 다시 비교했습니다.
각 시드에서는 두 알고리즘의 팀·홈/원정 배정을 교환했습니다.

| 비교 | 새 예제 승/무/패 | 승점 비율 | 득실점 차 |
|---|---|---|---|
| 첫 20경기, 시작 시드 310000 | 15승 2무 3패 | 80.0% | +50 |
| 별도 40경기, 시작 시드 710000 | 22승 4무 14패 | 60.0% | +15 |
| 위 60경기 합계 | 37승 6무 17패 | 66.7% | +65 |

승점 비율은 `(승 + 0.5 × 무) / 경기 수`입니다. 위 표는 빠른 비교 모드에서 측정한 결과입니다.
별도로 첫 시드의 2경기를 실제 프로세스 격리 방식으로 재실행했고, 경기별 점수·승자가 일치했습니다.
이는 중복 검증이므로 60경기 합계에 다시 더하지 않았습니다.

10개 구단 모두 실제 제출 검사에서 공격·수비가 통과했고 경고가 없었습니다.
지친 선수, 빈 맞대결 표, 시작 인덱스 7인 조건에서도 유효한 명단과 같은 rng의 재현성을 확인했습니다.
비교 경기에서 양쪽 모두 폴백은 0회였습니다.

격리 방식 2경기에서 새 예제의 36회 호출은 평균 1.63초, 최대 1.92초였습니다(프로세스 시작 비용 포함).
빠른 모드의 별도 40경기에서는 평균 약 0.124초로, 기존 예제의 약 0.090초보다 계산량이 늘었습니다.
PC 부하와 환경에 따라 시간은 달라집니다.

이 표본에서는 개선형이 앞섰지만 모든 팀 조합·시드에서 우세하거나 통계적으로 확정적인 개선이라는 뜻은 아닙니다.
